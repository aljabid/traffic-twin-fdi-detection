# Hardware testbed plan (ELEGOO Mega 2560 kit, later ESP32)

Goal: answer the reviewer question "was any of this run on real devices?"
with three measurements, and give the paper (and the thesis defence) a
working end-to-end demonstration. Status 2026-10-15: kit received, board
not yet connected; ESP32 not yet bought. Nothing below has been run yet.

## Devices

| Device | RAM or clock | Radio | Role |
|---|---|---|---|
| ELEGOO Mega 2560 (ATmega2560) | 8 KB / 16 MHz, 8-bit | none (USB serial) | constrained roadside sensor node; ECDSA timing; live demo |
| ESP32 (plain) | 520 KB / 240 MHz | WiFi, BLE | mid-range node; ML-KEM or ML-DSA timing; second device |
| ESP32-S3 N16R8 | 512 KB + 8 MB PSRAM | WiFi, BLE | high-end node; full post-quantum suite |

## H1. Cryptography on the device (fills the "lower bound" gap in §6.10)

Measure, on each board, mean and spread over at least 100 runs:

- ECDSA-P256 sign and verify (micro-ecc on the Mega; mbedTLS on ESP32);
- ML-KEM-768 keygen, encapsulate, decapsulate (ESP32). On the Mega this is
  not expected to fit: even ML-KEM-512 decapsulation needs 9.4 KB of stack
  in PQClean reference C (Chhetri et al., 2026), more than the board's 8 KB
  of RAM. Report the attempt;
- ML-DSA-65 sign and verify (ESP32 only; signing needs about 78 KB of
  stack, so the FreeRTOS task stack must be raised; on the Mega it cannot
  fit). Use at least 1,000 signatures: signing time has a long tail from
  rejection sampling, and 100 runs under-report it;
- HMAC-SHA256 per message (the session-key design §6.10 recommends);
- energy per operation with an INA219 current sensor, if bought.

Expected outcome for the paper: a table of real device timings beside the
link-time lower bounds, and a measured statement that per-message
post-quantum signatures do not fit the 8-bit class while per-session
signatures plus per-message MACs do.

## H2. Live detection on real sensor data

Sensor node (Mega) reports, ten times a second, over USB serial:

| Field | Sensor in the kit | Notes |
|---|---|---|
| device id | RC522 RFID card UID | identity spoof = report another card's UID |
| timestamp | DS1307 real-time clock | time shift or backdate = offset the clock |
| position, speed | HC-SR04 ultrasonic (distance of a moving object) | speed from successive distances |
| occupancy | photoresistor light gate | fraction of the last second the beam is blocked, as a loop detector reports |
| acceleration (optional) | GY-521 (MPU-6050) | for a plausibility check on reported speed changes |

Laptop side: smart_city_security.hardware.serial_bridge reads the lines,
builds the same Telemetry messages the paper uses, runs the twin and the
detector, and sends the verdict back; the node shows it on the LCD and
sounds the buzzer. Attacks are switched on from the membrane keypad
(1 congestion spoof, 2 clear-road spoof, 3 time shift, 4 identity spoof,
0 off). The node marks which messages it falsified, which is ground truth
for scoring only and never a detector input.

Procedure: (1) record 20-30 minutes of benign data with objects moving in
front of the sensors; (2) train Hybrid+ on the first part, with attack
examples generated by our attack code on that recording; (3) live phase
with attacks switched on and off by keypad. Report benign false-alarm rate,
detection rate and time to first alarm per episode, and end-to-end latency
(sensor reading to LCD alarm).

What this adds, honestly stated: real sensor noise and a real timing path
on a toy-scale scene. It is not a traffic field test.

## H3. Two-device attack (needs two boards)

Two nodes report the same scene; one is compromised. Tests whether
cross-device consistency catches what single-sender features miss (the
constant-offset weakness in §6.5). Optional, after H1 and H2.

## Order of work

1. Connect the Mega; install arduino-cli; upload a blink test.
2. H1 on the Mega (ECDSA, ML-KEM-512 attempt, HMAC).
3. Build the sensor node; H2 recording, training, live run.
4. ESP32 arrives: H1 on ESP32; optional H3.

## Results

### H1 on the Mega 2560 (measured 2026-10-15)

firmware/crypto_bench (micro-ecc 1.0.0 for ECDSA, Rhys Weatherley's
Crypto 0.4.0 for SHA-256 and HMAC), 16 MHz ATmega2560, one 64-byte message
standing in for an encoded telemetry message. Raw output:
results/hardware/crypto_mega.txt.

| Operation | Runs | Mean (ms) | Min | Max |
|---|---|---|---|---|
| SHA-256, 64 B | 1,000 | 21.5 | 21.5 | 21.7 |
| HMAC-SHA256, 64 B | 1,000 | 53.7 | 53.7 | 53.8 |
| ECDSA-P256 key generation | 5 | 4,357.6 | 4,356.1 | 4,358.3 |
| ECDSA-P256 sign | 20 | 4,693.1 | 4,690.5 | 4,695.7 |
| ECDSA-P256 verify (20/20 valid) | 20 | 5,154.2 | 5,154.2 | 5,154.4 |

- At the 10 Hz message rate (100 ms per message), signing every message is
  impossible on this class of device even with classical ECDSA (47 times
  the budget). Post-quantum schemes do not fit in its 8 KB of RAM at all.
- A per-message HMAC fits (54 ms), using about half the budget. A session
  set-up with one ECDSA signature costs about 5 s, once.
- Together this supports the paper's recommendation, now with a measurement:
  per-session signatures and per-message MACs are the only workable design
  on the constrained class.
- The SHA-256 time is library-specific (an unoptimised portable
  implementation); faster AVR assembly versions exist, so these are
  conservative figures.

### H2 recording (2026-10-15)

Four three-minute sessions of a hand-moved object along a bench track
(results/hardware/benign_1..4.csv, joined in recording.csv, 6,077
readings at 10 Hz). Sessions 1-2 have no occupancy signal (a fixed shadow
threshold was set too high); sessions 3-4 use an adaptive room-light
threshold and record shading about 40% of the time. Hybrid+ trained on the
first 70% (6.8 s) gave a 10.2% per-message benign false-alarm rate on the
held-out 30%. These figures are void: see the clock fault below.

### Clock fault (found 2026-10-20)

The node held its time in a float (rtcSeconds). A 32-bit float has a
24-bit mantissa, so an epoch value near 1.76e9 rounds to 128 s steps and the
RTC field barely moved; the bridge then built timestamps as rtc + millis % 1000,
which ran backwards every second. All timing features were meaningless, and
the first live run (live_1.csv: 7-10% detection, the same as the benign
false-alarm rate) is discarded. Fixes: unsigned long in the firmware, and
serial_bridge --clock millis, which stamps readings from the millisecond
counter so the old recordings stay usable (a board reset continues the time
line).

### H2 model and offline check (2026-10-20)

Trained on sessions 3-4 only (recording_occ.csv, 3,088 readings; sessions
1-2 have no occupancy), --clock millis, the four rehearsal families at road
scale: results/hardware/hybrid_plus_v2.pkl. Held-out check, training on
session 3 + the first 60% of session 4 and replaying the node's attacks on the
rest (15 s on / 15 s off):

| Training | benign FPR | congestion | clear-road | identity |
|---|---|---|---|---|
| sessions 1-4, road scale | 0.102 | 0.820 | 1.000 | 0.137 |
| sessions 1-4, speed biases × 0.2 | 0.102 | 0.803 | 1.000 | 0.130 |
| sessions 3-4, road scale | 0.058 | 0.733 | 1.000 | 0.073 |
| sessions 3-4, speed biases × 0.2 | 0.055 | 0.727 | 1.000 | 0.073 |

Scaling the rehearsal attacks to the bench does not matter; dropping the
sessions without occupancy brings the false-alarm rate to the budget.

serial_bridge live --clock millis --model results/hardware/hybrid_plus_v2.pkl
--schedule 0:30,1:30,0:30,2:30,0:30,4:30, object moved by hand, analysed
with scripts/analyse_live_run.py:

| | live_2 | live_3 |
|---|---|---|
| benign messages or false-alarm rate | 802 / 4.7% | 794 / 3.1% |
| benign, 3-of-5 persistence | 0.13% | 0.0% |
| congestion spoof (rehearsed) | 83.0% | 88.0% |
| clear-road spoof (rehearsed) | 100% | 100% |
| identity spoof (not rehearsed) | 6.5% | 5.8% |

Identity spoof is flagged at the benign rate, i.e. not detected (the
script's "episode detected" for it is a chance false alarm).

### H1 on the ESP32 (measured 2026-10-20)

DFRobot FireBeetle 2 ESP32-E (ESP32-WROOM-32E, ESP32-D0WD-V3 rev 3.1,
240 MHz, 520 KB SRAM, no PSRAM), CH340K USB bridge (driver from WCH),
arduino-cli with the esp32 core 3.3.12 (separate config file
--config-file <esp32-config>.yaml, FQBN
esp32:esp32:firebeetle32). firmware/crypto_bench_esp32: mbedTLS for
SHA-256, HMAC and ECDSA-P256; PQClean "clean" C for ML-KEM-768 and
ML-DSA-65; times in CPU cycles; each group in its own task on a 104 KB stack.
Raw output: results/hardware/crypto_esp32.txt (cycles; ms = cycles / 240,000).

| Operation | Runs | Mean (ms) | Median | p99 | Max |
|---|---|---|---|---|---|
| SHA-256, 64 B | 1,000 | 0.047 | 0.047 | 0.052 | 0.211 |
| HMAC-SHA256, 64 B | 1,000 | 0.141 | 0.140 | 0.145 | 0.219 |
| ECDSA-P256 keygen | 20 | 144.4 | 144.4 | 145.3 | 145.3 |
| ECDSA-P256 sign | 200 | 155.9 | 156.0 | 156.3 | 156.3 |
| ECDSA-P256 verify (200/200 valid) | 200 | 309.4 | 309.4 | 309.5 | 309.6 |
| ML-KEM-768 keygen | 1,000 | 8.88 | 8.87 | 8.98 | 9.38 |
| ML-KEM-768 encaps | 1,000 | 10.29 | 10.29 | 10.30 | 10.39 |
| ML-KEM-768 decaps (1,000/1,000 match) | 1,000 | 12.32 | 12.32 | 12.33 | 12.41 |
| ML-DSA-65 keygen | 100 | 27.37 | 27.37 | 27.38 | 27.65 |
| ML-DSA-65 sign | 1,000 | 85.98 | 72.19 | 278.69 | 489.45 |
| ML-DSA-65 verify (1,000/1,000 valid) | 1,000 | 27.63 | 27.63 | 27.63 | 27.71 |

Peak stack: ML-DSA-65 79,956 B, ML-KEM-768 15,012 B, ECDSA 2,468 B.
267 of 1,000 ML-DSA-65 signatures took over 100 ms, 41 over 200 ms.

- Every post-quantum operation fits; key establishment is cheap (~31 ms for
  keygen + encaps + decaps).
- ECDSA-P256 is slower than ML-DSA-65 on this chip (no ECC accelerator).
- Per-message signatures miss the 100 ms budget (ECDSA always, ML-DSA-65 for
  27% of messages); a per-message HMAC costs 0.14 ms.
- Two firmware pitfalls on the way: a global named times collided with the
  C library's times() and corrupted the timing array, and a 160 KB task
  stack could not be allocated (largest free block ~108 KB); the stack is now
  allocated once and reused.
